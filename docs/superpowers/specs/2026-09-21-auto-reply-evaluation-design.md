# 客服自动回复质量评估流水线设计

## 1. 目标与边界

本项目将业务方对“准确、有用、语气好、不瞎编”的模糊要求转换为可运行、可解释、可复现的评估流水线，并对 `task3_auto_replies.json` 中的 20 条回复生成报告。

本次交付不接入真实订单、商品、平台政策或客服操作系统，因此对外部事实只能识别“是否缺少证据”，不能在没有知识库的情况下断言其真假。

`task3_human_ref.json` 只用于验证评分排序和问题识别，不作为事实知识库，也不参与单条回复的评分。原因是该文件包含无法从当前输入验证的商品参数、赔付金额、质保期和占位符。

## 2. 方案选择

采用混合式架构：

- 默认使用确定性 mock 评估器，无需 API Key 即可复现完整报告。
- 可选使用 Qwen LLM Judge 增强语义判断。
- 两种评估器实现相同接口，产生相同的结构化结果，报告层不依赖具体评估后端。
- Qwen 通过 OpenAI-compatible HTTP API 调用，不在仓库中保存密钥。

Qwen 运行参数：

- `QWEN_API_KEY`：用户自行设置。
- `QWEN_BASE_URL`：可覆盖，默认为阿里云 DashScope OpenAI-compatible 端点。
- `QWEN_MODEL`：可覆盖，不把会随时间变化的“最新模型”写死为业务规则。
- 未设置 `QWEN_API_KEY` 时，Qwen 模式明确报错，不悄然回退到 mock，避免用户误判实际使用的评估器。

## 3. 评估指标

每项指标先按 0–4 级量表评分，再乘以 25 转换为 0–100 分。每项分数必须同时输出证据和理由。

### 3.1 意图准确性（25%）

定义：回复是否理解并正面回应用户的核心诉求。

量化要点：

- 是否直接回答主要问题。
- 是否覆盖一条消息中的多个意图。
- 问题信息不足时，是否追问真正必要的信息。
- 是否用通用说明替代对具体个案的处理。

选择理由：“准确”不应等同于与参考文本的语言相似度，而应衡量是否理解了用户真正要解决的问题。

### 3.2 有用性与服务闭环（30%）

定义：回复是否让用户更接近解决问题，而不是只把责任转回用户。

量化要点：

- 是否给出明确、可执行的下一步。
- 是否索取订单号、商品、账号等解决问题所需的最小信息。
- 是否主动承接处理，或至少给出完整自助路径。
- 是否只说“查详情页、自己联系、继续等待、再找客服”。

选择理由：人工标注中最高频的缺陷是“信息本身没错，但没有解决用户的具体问题”。

### 3.3 事实依据与幻觉风险（30%）

定义：回复中可验证的声明是否有可用证据，是否存在无依据的政策、时效、金额、商品参数、能力或执行结果承诺。

量化要点：

- 抽取数字、时间、金额、政策、材质、质保和服务能力声明。
- 判断声明是否来自用户问题或未来可接入的知识上下文。
- 区分“缺少证据、需要核实”与“已确认为虚假”；当前数据只支持前者。
- 识别“我已处理、会自动提醒、可申请额外补偿”等可能超越系统权限的能力声明。

选择理由：将“不瞎编”与意图准确性拆开，才能区分“答对了问题但事实无依据”和“事实没错但没帮上忙”。

### 3.4 语气与情绪适配（10%）

定义：回复是否礼貌，并且在投诉、焦虑、安全或连续出错场景中体现与情境相符的共情和安抚。

量化要点：礼貌、共情、情绪强度匹配，以及是否出现推责、说教或机械话术。

### 3.5 清晰与简洁（5%）

定义：回复是否结构清晰、易于执行，且不用无关的内部话术增加用户的理解成本。

量化要点：步骤可读性、长度、重复、内部流程话术和与当前问题无关的陈述。

## 4. 综合分、优先级与风险门槛

综合分公式：

```text
overall =
  intent_accuracy * 0.25 +
  usefulness * 0.30 +
  groundedness * 0.30 +
  tone * 0.10 +
  clarity * 0.05
```

优先级为：事实安全 > 意图准确与实际帮助 > 语气 > 表达形式。

如检测到高风险虚构承诺、明显错误的安全建议或宣称已执行实际未执行的操作，记录 `critical_fail`，并将综合分上限设为 59。普通的未验证政策或参数记录为 `unsupported_claim`，降低事实依据分，但不直接判定为虚假。

## 5. 系统组件

### 5.1 输入与验证

- 读取自动回复 JSON 和可选人工参考 JSON。
- 检查 JSON 顶层结构、必填字段、字段类型、ID 唯一性和两份数据的 ID 对齐。
- 输入不合法时返回可定位到文件、case 和字段的错误，不生成部分报告。

### 5.2 统一 Judge 接口

Judge 接收用户问题、自动回复和可选知识上下文，返回：

- 五项 0–100 分数。
- 每项简短理由和文本证据。
- 标准化风险标签。
- `critical_fail` 与原因。
- 评估器名称、模式、模型和提示词版本等元数据。

### 5.3 Mock Judge

Mock Judge 使用不依赖 case ID 的通用信号：

- 具体个案识别：“我的、这个、那个、上次、已经”等表达。
- 信息不足识别：需要订单号、账号、具体商品或用户选择。
- 主动承接与自助路径信号。
- 自助转移信号：仅建议查详情页、联系其他客服或继续等待。
- 多意图覆盖。
- 投诉、焦虑、安全、连续失败和操作困难等情绪场景。
- 数字、时间、金额、政策、材质、质保和能力承诺的事实声明。

Mock 模式的分数与评语完全由可见规则决定，相同输入必须产生字节级稳定的核心评分结果。

### 5.4 Qwen Judge

Qwen Judge 使用版本化的系统提示词和 JSON Schema，要求模型：

- 仅根据用户问题、自动回复、评分量表和可选知识上下文判断。
- 不把人工参考答案提供给评分请求。
- 不依赖自身记忆来认定平台政策或商品事实。
- 对无证据的外部事实使用 `unsupported_claim`，而不是断言为错误。
- 返回严格 JSON，返回后再经本地 schema 校验和分数边界校验。

HTTP 请求设置明确超时。身份验证失败、限流、超时、非 JSON 响应或 schema 不合法均记录为当次运行失败，不用 mock 结果掩盖。

## 6. 人工参考验证

由于人工文件没有数值标注，系统将标注分析转换为一个独立、可审查的三档验证集：

- 正向组：标注明确说明“处理得不错、基本正确、质量尚可”。
- 中间组：有明确价值，但仍存在可改进的服务闭环问题。
- 负向组：标注明确说明“答非所问、正确但没用、把责任推给用户”等严重问题。

验证数据不参与评分。报告展示：

- 正向组与负向组的平均分差。
- 三档序数标注与系统综合分的 Spearman 相关系数。
- 主要人工问题标签与自动风险标签的匹配率。
- 所有不一致 case 及其原因，不隐藏不利结果。

由于样本仅 20 条且只有一组人工参考，相关系数只用作开发期方向性检查，不声称统计显著性。

## 7. 报告与交付物

一次运行生成：

- 机器可读的完整 JSON 结果。
- 每条 case 的 CSV 分数表。
- Markdown 评估报告。
- 包含图表和最差三条分析的自包含 HTML 报告。
- 开发工具截图和运行结果截图。
- README，说明指标、方法、局限性、Qwen 配置、运行命令和 AI 工具使用情况。

HTML 中的数据必须来自同一份 JSON 运行结果，不在页面内手工写结论。最差三条按综合分升序选取，同分时按 case ID 排序。

## 8. 错误处理与可复现性

- CLI 使用非零退出码区分输入错误、配置错误和 Judge 错误。
- 生成报告前先在内存中完成全部 case 评分；任一 case 失败时不宣称本次报告完整。
- Mock 评估固定规则版本。
- Qwen 结果记录模型名称、提示词版本、运行时间和温度。
- 运行结果不记录 API Key，错误消息也必须避免回显密钥。

## 9. 测试策略

使用 Python 自带 `unittest`，避免为默认运行引入额外依赖。

覆盖范围：

- 合法与非法输入 schema、重复 ID 和 ID 错配。
- 五项分数范围与加权公式。
- `critical_fail` 分数上限。
- Mock 结果确定性。
- 具体个案、自助转移、必要追问、多意图、情绪适配和无证据声明的代表性规则。
- Qwen 端的缺少密钥、HTTP 失败、非 JSON 响应与 schema 错误；网络请求在测试中使用本地替身，不消耗真实 API 额度。
- 20 条输入的端到端报告生成。
- 最差三条选取规则与所有报告格式的关键字段一致性。

## 10. 局限性与后续改进

- 没有商品库、订单系统和政策知识库时，只能识别待核实声明，不能完成真实事实核验。
- 规则对委婉表达、反讽和隐含多意图的识别不稳定。
- 仅有 20 条样本和单一人工参考，无法估计标注者一致性，也不能代表真实线上分布。
- 是否应“主动代办”取决于客服系统权限；生产化时必须把工具能力清单作为评估上下文。
- LLM Judge 会受模型版本、提示词和采样波动影响，生产中应固定版本、重复采样、持续人工抽检。
- 文本离线分数不等于业务结果；后续需加入问题解决率、重复咨询率、转人工率、用户满意度和安全事故率。

## 11. 验收标准

- 默认 mock 命令在无网络、无 API Key 时可对 20 条记录完整评分。
- 每条记录有五项分数、综合分、证据、问题标签和改进建议。
- 报告包含整体得分、各指标分布、最差三条及分析。
- 报告明确区分“被证明错误”与“无证据、待核实”。
- 人工参考验证与实际评分数据隔离。
- 所有自动化测试通过，README 的命令从干净环境可执行。
- Qwen 后端可由用户通过环境变量配置，不提交密钥。
- 交付 README、开发工具截图、运行结果截图和全部本地源码。
